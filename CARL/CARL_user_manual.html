Overview

CARL (Classification AI-Accessible Research Laboratory) is a desktop application for taxonomists. CARL's central concern is the taxon as a nomenclatural entity. Every taxon in CARL has a name, a rank, a status (existing in the literature or new to science), and optionally a set of formal relationships to other taxa — synonymy, hierarchical membership, renaming, or division. These declarations are stored in a BEGIN CARL; block inside a standard #NEXUS file and constitute the foundation of all CARL work.

Character-state data — the morphological matrix used to generate descriptions, keys, and comparisons — is optional. A taxonomist may associate any taxon with a row in the NEXUS DATA block, but is not obliged to do so. With properly declared taxa, CARL can retrieve published records from external biodiversity databases, manage synonymy, and build a formal nomenclatural hierarchy regardless of whether any character data is present. The simplest valid file CARL will load is:

#NEXUS

BEGIN CARL;
END;

This file declares no taxa and contains no data. It is a complete and valid starting point. From here, a user can declare taxa in the Nomenclature tab, enter character data in the Editor, link taxa to data rows, and save — CARL writes the complete #NEXUS file, including the DATA block and all blocks it manages.

What CARL can do

CARL's capabilities fall into two layers. Part A of this manual covers everything that requires no language model:

  • Manage nomenclatural declarations — define, rename, synonymise, group, and divide taxa via the Nomenclature tab
  • Enter and edit character-state data — via the spreadsheet Editor tab
  • Generate raw descriptions — programmatic, matrix-derived descriptions of taxa or groups
  • Compare and distinguish taxa — character-by-character comparisons; lists of distinguishing characters
  • Diagnose taxa — find the minimal character set that uniquely identifies a taxon
  • Generate identification keys — dichotomous keys (binary or multi-arm, using IG — Information Gain (Shannon) — or DG — Diversity Gain (Simpson's Index) — scoring) for any selection of taxa or groups, plus a Multi-Access Key (polyclave) for interactive elimination-based identification in any character order
  • Retrieve external records — fetch Darwin Core data from GBIF, Catalogue of Life, ZooBank, and ITIS; review, resolve, and export
  • Look up the Codes of Nomenclature — retrieve the articles of the ICZN, ICN, ICNP and ICVCN that best match a question, without a language model (see Using the Chatbot without a Language Model)

Part B covers the additional functionality that language models provide:

  • Narrate analyses — convert raw programmatic output into fluent natural-language descriptions, comparisons, and keys
  • Verify output — a second model reviews the first model's output against the raw data, flagging errors and omissions
  • Carl the chatbot — a conversational assistant for taxonomy and biology questions, with optional grounding in the official nomenclatural codes

Part A — CARL without AI

All features described in this section require no language model and no API key. Biodiversity database retrieval requires an internet connection; all other analyses run entirely offline.

NEXUS Files and CARL

CARL works with standard #NEXUS files. A CARL-enabled NEXUS file may contain any combination of three blocks:

  • BEGIN DATA; — the character-state matrix (taxa × characters). Optional.
  • BEGIN CARL; — nomenclatural declarations. Required for CARL's full functionality; auto-generated if absent when the user saves from the Nomenclature tab.
  • BEGIN SETS; — optional; may contain CHARSET declarations that group characters into named sets. In Descriptions, each set becomes a separate labelled paragraph, in declaration order; characters not listed in any set are collected under a final Other Features paragraph. Character numbers are 1-based and ranges use a hyphen (e.g. 37-47). 
    BEGIN SETS;
  CHARSET "Habitation" = 1 2;
  CHARSET "Mouthparts" = 37-47;
  CHARSET "Sternum" = 33-36;
  CHARSET "Legs" = 15-30;
  CHARSET "Spinnerets" = 3-14;
END;
  • BEGIN ASSUMPTIONS; — optional; may contain WTSET statements that control character weighting for CARL analyses. Only three labels are recognised: WTSET descriptions (characters with weight 0 are excluded from description generation), WTSET compare (characters with weight 0 are excluded from taxon comparison and diagnosis), and WTSET key (arbitrary weights; 0 = hard exclusion, higher values increase selection priority). All other content in the block is ignored. The block is hand-authored and is not written or modified by CARL on save. 
    BEGIN ASSUMPTIONS;
  WTSET descriptions = 0:1;
  WTSET compare = 0:1 2;
  WTSET key = 0.5:1-4 29, 5:21 23, 10:5 8 19 20;
END;

CARL reads all blocks on file load. If a BEGIN CARL; block is absent but a DATA block is present, CARL enters Build mode — DATA row labels appear as unassigned raw material in the Nomenclature tab. If neither block is present, the file is rejected as invalid.

Loading an existing NEXUS file? If you have a matrix from MrBayes, TNT, PAUP*, or any other NEXUS-compatible program, CARL can load it in Build mode and let you add nomenclatural declarations without modifying your original analytical workflow.

The minimum file

The simplest file CARL will load is:

#NEXUS

BEGIN CARL;
END;

This file declares no taxa and contains no data. It is a valid starting point for a project built entirely within CARL. Declare taxa in the Nomenclature tab, add character data in the Editor, and save — CARL writes the complete NEXUS file, including the DATA block.

NEXUS DATA block format

When a DATA block is present, CARL expects the following structure:

#NEXUS

BEGIN DATA;
DIMENSIONS NTAX=3 NCHAR=3;
FORMAT DATATYPE=STANDARD MISSING=M GAP=-;
CHARSTATELABELS
    1 "Number of anterior lateral spinnerets" / 0 "two" 1 "one",
    2 "Posterior median spinnerets" / 0 "absent" 1 "present",
    3 "Shape of posterior median spinnerets" / 0 "digitiform" 1 "broad, with obliquely truncated tips",
;
MATRIX
Taxon_A 10N
Taxon_B M1(0,1)
Taxon_C 00N
;
END;
  • Character and state labels must be in quotation marks.
  • M = missing or unknown; N = not applicable (the character does not apply to this taxon).
  • Polymorphic states are listed in parentheses: (0,1).
  • Taxon names in the MATRIX block must not contain spaces — use underscores (e.g. Latrodectus_mactans).
Character and state labels are passed directly to language models in Part B. Labels written as natural phrases ("spinnerets present", "two anterior lateral spinnerets") produce better narrated output than terse codes. See Part B for guidance on iterating style.

The CARL Block

The BEGIN CARL; block is CARL's nomenclatural layer — a flat list of statements describing the taxonomic status and relationships of named entities. It lives inside the NEXUS file alongside any DATA block and is ignored by other NEXUS software.

There are two ways to author CARL block statements:

  1. Via the Nomenclature tab UI — the recommended approach. CARL generates the syntax automatically from form inputs and writes syntactically complete blocks on save.
  2. By hand-editing the .nex file — useful for scripted workflows or bulk edits. Hand-edited files may use the shorthand omission rules described below; CARL expands these to full form on the next save.

Two domains: Data and Nomenclature

CARL distinguishes two independent domains:

  • Nomenclature — taxa with names, ranks, and relationships to each other. Lives in the BEGIN CARL; block.
  • Data — rows in the NEXUS DATA matrix. Each row has a label (called a DataID or DATA variable name) and a set of character states. These labels are arbitrary strings — Taxon_A, SP3, or Hexurella are all equally valid DataIDs.

The two domains are connected by data pointers ([&D ...] annotations) on each CARL statement, which link a nomenclatural name to a DataID. The same string can appear on both sides of a pointer (e.g. [&D Hexurella=Hexurella]) — this is not tautological. The left-hand name is a nomenclatural entity; the right-hand name is a DATA row label that happens to share the same string.

A taxon declared with [&D Name=none] — no DataID assigned — is a CARL-only taxon. It has full nomenclatural standing and can be fetched from external databases, but cannot participate in character-based analyses (descriptions, keys, comparisons, diagnoses) until linked to a DATA row.

Statement syntax

Every CARL statement follows this general form:

<Name> <is|is_new> <rank> [<action> <Name>, <Name> ...] [&D <Name=DataID>: <Name=DataID>, ... #comment];
PartRequired?Meaning
<Name>Yes Nomenclatural name of the subject taxon
is or is_newYes is = existing published name; is_new = new to science, not yet in any external database
<rank>Yes Any rank string. Standard Darwin Core ranks map to DWC fields on export; non-standard ranks (e.g. infraorder, clade) are stored as-is.
Action keyword + object listNo Absent for definition statements; present for renames, synonymizes, includes, divides
[&D ...]Recommended Data pointer — links nomenclatural names to DataIDs. May be omitted if all names were already declared in a prior statement.

The five statement types

1. Definition (no action keyword)

Declares a taxon's name, status, rank, and data pointer. Acts as the entity registry.

Hexurella is_new genus [&D Hexurella=Hexurella];
Mecicobothrium is genus [&D Mecicobothrium=Mecicobothrium];
Hexurilliana is_new genus [&D Hexurilliana=none];

is_new taxa are new to science — retrieval from external databases is blocked. is taxa are existing published names and are retrievable normally. none means no DataID is currently assigned.

2. Renames

Replaces an old name with a new name. The old name is retired and never shown in the Derived View. The new name may be is (an existing name change) or is_new (a new combination / nomen novum).

Atticus is genus renames Atypus [&D Atticus=none: Atypus=Atypus_data];
Atticus is_new genus renames Atypus [&D Atticus=none: Atypus=Atypus_data];

Data inheritance rule: if the new name has no DataID of its own (none) but the old name has a DataID, the new name inherits the old name's DataID at display time.

A particularly instructive case is swapping the names of two taxa:

Systematicus is genus renames Biologica [&D Systematicus=Biologica: Biologica=none];
Biologica is genus renames Systematicus [&D Biologica=Systematicus: Systematicus=none];

Here the matrix rows are labelled Systematicus and Biologica; after the renames action each taxon acquires the DataID previously held by the other. To avoid circularity, each renames statement must assign =none for one taxon.

3. Synonymizes

Places one or more synonyms under an accepted name, creating a synonymy group. The accepted name (subject) appears as a group header labelled <taxon_name>_syn; each synonym appears as a sub-row labelled <taxon_name>_syn_<member>. All objects must have status is.

Illawarra is genus synonymizes Hexura, Mecicobothrium
    [&D Illawarra=none: Hexura=Hexura_data, Mecicobothrium=Mec_data];

DataID rule: members may retain their own DataIDs. A pre-coded DataID for the accepted-name concept may be assigned explicitly to the subject; otherwise the subject defaults to none.

4. Includes

Designates a higher-rank taxon as a formal group containing listed lower-rank taxa. Included taxa appear both under the group header and as their own standalone rows elsewhere in the Derived View.

Mygalomorphae is order includes Atypidae, Hexurellidae [&D Mygalomorphae=none: ];

Member names already declared elsewhere do not need to be re-declared in the data pointer.

5. Divides

Splits a taxon into two or more daughter taxa. The parent (subject) is retired as an active taxonomic concept but remains visible in the Derived View as a group header, with daughters nested beneath it. This allows the parent's historical database records to be retrieved (if is) or its Darwin Core fields to be populated (if is_new).

By default, CARL pre-fills the first daughter with the parent's name, reflecting the nomenclatural convention that one daughter carries continuity with the parent. The first daughter also inherits the parent's DataID as a starting point; additional daughters default to DataID=none.

Hexufilia is_new genus [&D Hexufilia=Hexurella_daughter];
Hexurella is genus divides Hexurella, Hexufilia [&D Hexurella=none: Hexurella=Hex_data];

OR (if the pre-division codings should remain with the parent for historical retrieval):

Hexurella is genus divides Hexurella, Hexufilia [&D Hexurella=Hex_data: Hexurella=none];

DataID rule: because the parent and the first daughter initially point to the same DataID, a shared-DataID warning fires on save. Resolve by deciding which entity should retain the DataID:

  • If the pre-division data best represent the first daughter, set the parent's DataID to none and retain the DataID on the daughter.
  • If the pre-division data should remain with the parent (for historical retrieval), set the first daughter's DataID to none or assign it a new row.
  • If neither daughter's biology matches the pre-division codings, set both to none and assign DataIDs afresh.

The dataID for Hexufilia is omitted from the divides declaration above because Hexufilia is independently declared in the preceding statement.

Named block headers such as [# DEFINE TAXA ], [# RENAME TAXA ], [# UNITE TAXA ], and [# DIVIDE TAXA ] are treated as comments by the parser. They have no syntactic effect but help organise a hand-edited CARL block for human readers. CARL's UI does not produce them automatically.

Data pointer rules

The [&D ...] annotation maps nomenclatural names to DataIDs:

  • Left of : — DataID for the subject (name before the action keyword)
  • Right of : — DataIDs for the objects (names after the action keyword), comma-separated
  • The colon is always present when a pointer block appears, even if one or both sides are empty
  • =none — no DataID assigned to this name

Omission rule: if a name was already declared in an earlier statement, its pointer may be omitted from the bracket. [&D :] (both sides empty) is valid when all names have been previously declared.

Shared DataID warning: if two taxa point to the same non-none DataID, CARL issues a warning at load and save: "Taxa X and Y both point to DataID Z — they will be analytically indistinguishable."

Preclusion statements

Preclusion statements may appear anywhere in the BEGIN CARL; block body (typically after all taxon declarations). They exclude characters from key building whenever a specified condition is met. Read as: "if character N has state S, then do not use characters X, Y, Z at this branch or below."

This models logical dependencies between characters. For example, if character 5 is "spinnerets present/absent" and characters 6–7 describe spinneret morphology, it is pointless to ask about morphology once absence is established:

5(0) precludes 6, 7

All numbers are 1-based, matching the CHARSTATELABELS numbering. The state index in parentheses is 0-based (0 = first state, 1 = second state, and so on).

Complete example

BEGIN ASSUMPTIONS;
  WTSET key = 0.5:1-4, 5:21 23, 10:5 8 19 20;
END;

BEGIN CARL;

Hexurella is_new genus [&D Hexurella=Hexurella];
Mecicobothrium is genus [&D Mecicobothrium=Mecicobothrium];

5(0) precludes 6, 7
8(0) precludes 9, 10
23(0) precludes 24, 25, 26

END;
High weights (10×, 5×) are appropriate for characters that are easy to observe in the field and reliably coded. Low weights (0.5) are useful for characters that are difficult to observe, subjective, or available for only some specimens.
Preclusion statements and WTSET key weights are parsed automatically on file load. No action is required in the UI — the Keys tab applies them immediately the next time a key is generated.

Nomenclature Tab

The Nomenclature tab is the landing tab of the File panel and the primary interface for authoring the BEGIN CARL; block. All nomenclatural declarations — taxon definitions, synonymy, hierarchical groupings, renames, and divisions — are made here. All taxon groups are expressed entirely within the BEGIN CARL; block via synonymizes and includes declarations.

Three areas

The Nomenclature tab presents three areas side by side:

Statements list
A scrollable list of all current CARL block declarations, one per line, using display labels. Select a statement and click Delete (or right-click → Delete) to remove it. Changes propagate immediately to the Derived View and Information tab — no manual refresh is needed.
Derived View
A treeview showing the materialised result of all declarations: group headers for synonymizes and includes actions with their members as children; individual taxa as leaf nodes. Greyed rows indicate is_new taxa or taxa with no DataID assigned. This is the same view that drives the Information tab. It is read-only in the Nomenclature tab — editing is done via the Statements list and the +Add dialog.
DataID Pool
Lists all DATA row labels from the loaded NEXUS matrix that are not yet assigned to any CARL entity via a [&D ...] pointer. Use this pool to identify unlinked rows when building declarations in a file that already has a DATA block.

Loading states

When a file is loaded, the Nomenclature tab enters one of three states:

A file with a CARL block but no DATA block is a valid Normal state. The Editor tab can create the DATA block from scratch.

Declaring a CARL-only taxon (is status, no DataID) queues it for retrieval in the Information tab — it will appear in the Derived View and can be fetched immediately.

Right-click context menu

Right-click any row in the Derived View to open a context menu. Options depend on the taxon's data state:

Non-greyed taxon (has a DataID):

  • View characters/states — read-only popup showing the taxon's coded character and state data from the matrix
  • Edit in Editor — switches to the Editor tab, scrolling to the row for this taxon's DataID. Edits made there are reflected in analyses once the file is saved.

Greyed taxon (no DataID assigned):

  • View characters/states — disabled (no data to show)
  • Create in Editor — switches to the Editor tab and appends a blank row. The new row is not automatically linked to this taxon (see below).
  • Link to data — opens a picker showing all unassigned DataIDs in the Editor. Selecting one assigns it as this taxon's data pointer ([&D Taxon=chosenDataID]).

Group header:

  • View members — lists all member taxa with their current data states
Why isn't Create in Editor linked automatically? You may create several rows in the Editor before deciding which belongs to which taxon. An automatic link would make assumptions you have not confirmed. Use Link to data when you are ready to assign the row.

Editor Tab

The Editor tab is the data-entry surface for the NEXUS character-state matrix. It manages DataIDs (matrix row labels) and their coded character states. It has no knowledge of nomenclatural names — that relationship is handled separately in the Nomenclature tab via data pointers. All file saving is done from the Nomenclature tab; the Editor has no Save button.

The Editor serves two workflows:

  • Edit existing — load a NEXUS file via the Nomenclature tab, then switch to the Editor to modify coded states, rename DataIDs, or edit character and state labels.
  • Create new — click New to start a blank session, add characters with + Add Character, add DataIDs with + Add DataID, code states, then switch to the Nomenclature tab to save.

The Editor is split into two panes:

  • DataIDs (left pane) — a list of all matrix DataIDs, grouped visually by any synonymizes or includes declarations in the CARL block. Click a DataID to load its characters in the right pane. Right-click to rename.
  • Character/state canvas (right pane) — one row per character for the selected DataID. Click a character name to edit its label inline; right-click a character name to open the full Character Definition dialog; click a state value to edit the coded state.

When unsaved edits are pending, a label reads "Unsaved changes — use Nomenclature tab to save" in the toolbar. Switch to the Nomenclature tab and click Save or Save As… to write the changes to disk.

Character Definition dialog

Right-click any character name in the right pane to open the full Character Definition dialog. The same fields are available when adding a new character with + Add Character:

  • Character name — free-text label (pre-filled from column header)
  • Character type — multistate (default), continuous, or meristic
  • States — for multistate characters: an ordered list of state labels, numbered 0, 1, 2…
  • Notes — optional free-text annotation

Confirming the dialog updates the column header and writes the character definition to CHARSTATELABELS when the file is saved.

In this version of CARL, all characters are analysed as multistate characters regardless of the type setting. The character type is stored with the definition and will be used by the analysis engine in a future release.

Renaming DataIDs — CARL block propagation

If you rename a DataID row header in the Editor, CARL scans the loaded CARL block for all [&D ...] pointer references to the old name. A warning dialog lists all affected declarations:

"Renaming 'Hexurella_var' will also update 3 references in the CARL block. Continue?"

On confirmation, both the matrix row label and all CARL block pointer references are updated atomically before saving. On cancel, the rename is reverted.

Upgrading CARL-only taxa

A CARL-only taxon (declared with [&D Name=none]) can be promoted to a full matrix taxon:

  1. Right-click the greyed taxon in the Derived View (Nomenclature tab) → Create in Editor
  2. A new blank row is added in the Editor, ready for character-state entry
  3. Return to the Nomenclature tab, right-click the same taxon → Link to data → select the new row from the picker
  4. Save — the taxon's pointer is upgraded from none to the new DataID, and it becomes fully available for analysis

Information Tab

The Information tab retrieves published taxonomic records from external biodiversity databases for taxa declared in the CARL block. Its treeview mirrors the Derived View in the Nomenclature tab exactly — the same group structure, ordering, and display labels. Adding or removing a CARL declaration immediately updates both views.

Comparisons Tab

The Comparisons tab performs character-based comparisons between taxa. Like the Descriptions tab, it uses the shared left pane for taxon and group selection — see Descriptions Tab for details on how to select taxa and groups.

Output Mode and LLM Mode

The Output Mode and LLM Mode controls work identically to those in the Descriptions tab. Raw only produces deterministic output from the matrix; Raw + LLM passes that output to the Output Model for reformatting as prose. See Descriptions Tab and Analyses with AI (Part B) for full details.

Actions

Select the type of comparison via the Action radio buttons:

Compare

Produces a side-by-side character table for all selected taxa. Every character in the matrix is listed, with each taxon's coded state shown alongside. Identical states are displayed normally; differing states make differences immediately visible. Useful for a full character-by-character audit of any set of taxa.

Distinguish

Lists only the characters on which the selected taxa differ — characters where all selected taxa share the same state are suppressed. The output is a concise table of the characters that actually separate the taxa. Use this to quickly identify what makes a taxon distinctive within a chosen set.

Diagnose

Finds the minimal set of characters that uniquely identifies a focal (index) taxon against all members of a comparison group. This action has specific selection requirements:

  • Select exactly one taxon from the Taxa listbox — this is the index taxon to be diagnosed.
  • Select one or more groups from the Groups listbox — these provide the comparison taxa against which uniqueness is tested.

If no group is selected, CARL uses all other taxa in the list as the comparison set automatically — useful for a quick diagnosis of any taxon against the full dataset.

How the diagnosis works: CARL searches for character-state combinations that uniquely distinguish the index taxon from every comparison taxon. The search is combinatorial and proceeds in three passes:

  1. Single characters — any one character whose state in the index taxon is different from (or absent in) all comparison taxa.
  2. Pairs of characters — if no single character is sufficient, all pairs of characters are tested. A pair qualifies if no comparison taxon shares the same states as the index taxon for both characters simultaneously.
  3. Triples of characters — if no pair suffices, all three-character combinations are tested by the same logic.

All qualifying combinations at the smallest size found are reported, ranked by how well- sampled they are (combinations involving characters with more missing data in comparison taxa are ranked lower, as they are less reliable diagnostics).

Nearest neighbours: In addition to the diagnosis, CARL identifies comparison taxa that are most similar to the index taxon — those differing by the fewest character states. The Max differences spinner (range 1–20, default 3) controls the maximum number of character-state differences allowed for a comparison taxon to be listed as a nearest neighbour. Set this higher to see more distant neighbours; lower to see only the most similar taxa. Characters coded as missing (M) or not applicable (N) in either taxon are excluded from the difference count.

Interpreting the diagnosis. A size-1 diagnosis (one character suffices) is the strongest result — a single observable character distinguishes the taxon from all others. A size-2 or size-3 diagnosis means no single character is unique; the taxon is only distinguishable by a specific combination of characters. This can signal either genuine morphological similarity or gaps in the character set.
Missing data. A comparison taxon coded as missing (M) for any character in a diagnostic combination is excluded from the uniqueness check for that combination — CARL cannot determine whether it matches. Such taxa are flagged in the output. A comparison taxon coded as not applicable (N) is included in the check; N cannot match any real state and therefore reinforces the uniqueness claim.

Keys Tab

The Keys tab generates a branching identification key for the selected taxa and groups. At each node the algorithm scores all remaining characters and selects the highest-scoring one, recursively until every taxon has a unique path through the key. Taxa and groups are selected in the shared left pane — see Descriptions Tab for selection details. If nothing is selected, all taxa in the list are included.

Algorithm — IG (Shannon Information Gain)

The IG algorithm scores each candidate character by how much it reduces uncertainty about taxon identity at the current node. Characters that split taxa most evenly across their states score highest. The effective score incorporates a coverage adjustment (to penalise characters with much missing data) and the Repeat Weight (see below).

IG formula

score(c) = H(c) × (tdef / ttotal) × W × αuses

H(c) = −∑i pi × log2(pi)   where   pi = ni / tdef

ninumber of taxa with state i (definite states only; M, N, unknown excluded)
tdeftotal taxa with a definite state for character c
ttotaltotal taxa at the current node
H(c)Shannon entropy of the state partition (0 = all taxa in one state; maximum = perfectly even split)
Wcharacter weight from WTSET key in the ASSUMPTIONS block (default 1.0)
αRepeat Weight (default 0.05)
usesnumber of times c has been used on the path from root to this node

The character with the highest score is selected at each node. IG produces balanced, even-depth keys and is the recommended default.

Algorithm — DG (Diversity Gain, Simpson's Index)

The DG algorithm scores each candidate character by a lookahead ratio: how much between-group diversity does choosing this character now create across the remaining characters, relative to the residual within-group diversity? In other words, DG prefers characters whose split makes the resulting groups easier to distinguish with future characters. Because the score rewards a split for what it explains about the other characters, not for how evenly it divides the taxa, DG tends to single out distinctive taxa or small groups early, and its keys are usually less balanced than IG's. In simulations on a real grass-genus dataset, DG keys were on average no shorter than IG keys at the same Repeat Weight — slightly longer, and less balanced, as the number of taxa increased.

DG formula — step by step

1. Simpson's Diversity Index
For character j and a taxon set T, let n = number of taxa in T with a definite state (not M, N, or polymorphic), and ns = number of those taxa coded as state s:
D(j, T) = 1 − ∑s (ns / n)2

2. Partition and exact decomposition
Let c be the candidate character under evaluation. Define:
  Tdef = taxa with a definite state for c  (ndef = |Tdef|)
  G1, …, GK = partition of Tdef by state of c, one group per distinct state of c in Tdef (K = number of distinct states)

For any remaining character cj, D decomposes exactly as:
D(cj, Tdef) = Dwithin(cj | c) + Dbetween(cj | c)

3. Within-group and between-group components
Dwithin(cj | c) = ∑k (|Gk| / ndef)2 × D(cj, Gk)
  (pk2 weighting — not linear pk — makes the decomposition an exact algebraic identity)
Dbetween(cj | c) = D(cj, Tdef) − Dwithin(cj | c)

4. Summed across remaining characters Cafter = Cavailable \ {c}
Let Cafter = {c1, c2, …, cm} (m = |Cafter|). Then:
D̅B(c) = (1/m) × [Dbetween(c1 | c) + Dbetween(c2 | c) + … + Dbetween(cm | c)]
D̅res(c) = (1/m) × [D(c1, Tdef) + D(c2, Tdef) + … + D(cm, Tdef)]
D̅B is the mean between-group diversity activated across future characters by choosing c now. D̅res is the mean total diversity remaining across future characters.

5. Score
score(c) = (D̅B(c) / D̅res(c)) × (ndef / ntotal) × W × αuses
where ndef / ntotal is the coverage factor (penalises characters with many M/N codings), W is the user weight, and αuses is the cross-branch repeat penalty.

Edge case: if Cafter is empty, the lookahead is undefined; score falls back to D(c, Tdef) × (ndef / ntotal) × W × αuses.

The ratio D̅B / D̅res selects the character that maximises future between-group separation relative to future within-group confusion. DG is less sensitive to rare states than IG. It is offered as an alternative scoring rule, not as a way to shorten keys — use IG when the aim is the shortest and most balanced key.

Format

The Format radio buttons control the structure of each couplet:

  • Binary (dichotomous) — every couplet has exactly two leads labelled a and b. The conventional format for printed identification keys. When a character has more than two states, states are grouped into two contrasting leads. Familiar to users of traditional taxonomic keys.
  • Multi-arm — a couplet branches into one lead per distinct state. Produces shorter keys (fewer couplets to reach an identification) because multi-state characters resolve more taxa per node. Can be harder to navigate when a single character has many states.

Repeat Weight

The Repeat Weight (default 0.05, range 0–1) controls how strongly the algorithm discourages reusing a character that has already appeared on the current branch of the key. It acts as a multiplicative weight applied to the character's score for each prior use on the same branch:

  • First use at any node: full score (Repeat Weight raised to power 0 = 1 — no adjustment)
  • Second use on the same branch: score × α1 (e.g. ×0.05 at default)
  • Third use on the same branch: score × α2 (e.g. ×0.0025 at default)
A lower Repeat Weight means a greater penalty for reuse. At the default of 0.05, a character used once on a branch has only 5% of its base score — making reuse very unlikely. A value of 1 means no penalty (the character may be freely reused). A value of 0 hard-excludes the character after its first use.

Values near 0.05 (the default) almost completely prevent cross-branch repetition, producing diverse keys where each branch uses different characters. Values of 0.3–0.5 allow moderate repetition when no better alternative exists. Values near 1 allow the algorithm to freely reuse the most informative character at every level.

Character weights and preclusion

Character weights can be set in the BEGIN ASSUMPTIONS; block using WTSET key. Preclusion rules are written directly in the BEGIN CARL; block. See Preclusion statements in the CARL block section for full syntax and examples.

Plugins Panel

The Plugins panel runs external command-line programs from inside CARL, and lets you author the small JSON descriptor files that tell CARL how to drive them. The guiding principle is that a plugin wraps a standalone command-line program: CARL builds a command from your field values, runs it, streams its output, and displays the files it produces. Nothing about a plugin is specific to CARL's data model, so the same descriptor works for anyone who has that program installed.

The panel has two tabs — Run Plugin (configure and execute an existing descriptor) and Generate Descriptor (create or edit one).

Run Plugin tab

Click Open Descriptor… to load a plugin's .json file. CARL checks that the program is available and lists its option Sections on the left; selecting a section shows its Fields. A star (★) marks Common Options — the handful of fields most runs need.

As you fill in fields, CARL assembles the command in the editable command box at the top of the right pane. You can:

  • edit the command by hand — press Enter or Run to execute it (CARL parses the arguments itself and never invokes a shell);
  • click Rebuild to discard manual edits and regenerate the command from the current field values;
  • click Run to execute and Stop to terminate.

The right pane splits into Output — the live terminal (stdout and stderr, ending with a coloured exit-code line) — and Results. When the run finishes, CARL resolves the descriptor's output-file patterns and lists any files that exist. Selecting one shows an inline preview; the ⧉ Pop out button opens it in a dedicated window: text in an editable viewer (Save / Save As), trees in the interactive Phylogeny Viewer, and images in the Image Viewer. If no output prefix was set, use Add: Text… / Tree… / Image… to browse to a file manually.

Part B — CARL with AI

The features in this section require a language model — either a locally installed model via Ollama, or an API-hosted model via Groq, OpenAI, Anthropic, Google, or HuggingFace. No AI connection is needed for any feature in Part A.

AI in CARL

CARL uses language models as a post-processing layer, not as an analytical engine. All descriptions, comparisons, keys, and diagnoses are first generated deterministically from the character-state matrix, producing a Raw Output that is exact and reproducible. The language model is then given this Raw Output and asked to rephrase it as fluent natural-language prose.

Because the model works from a structured, verifiable input rather than from memory or general training knowledge, the risk of factual error is substantially lower than asking a model to generate a description from scratch. The Raw Output is always shown alongside any AI output so users can verify the model's work against the original data.

CARL uses language models for three purposes:

  • Narrating analyses — converting raw programmatic output into readable descriptions, comparisons, and keys
  • Verifying output — a second model reviews the first model's output against the raw data, flagging errors and omissions (Full mode)
  • Carl the chatbot — answering taxonomy and biology questions in conversation, with optional grounding in official nomenclatural codes

Setting Up Language Models

Language model settings are configured in Settings → LLM Settings. CARL supports two broad classes of model.

Local models via Ollama

Local models run entirely on your computer using Ollama. They require no API key and no internet connection. No data leaves your machine — making local models the privacy-preserving option. Their main limitation is capability: a model that fits on a laptop has substantially fewer parameters than a cloud-hosted one, and its prose may be less polished or consistent. Performance depends on available RAM (most models need at least 4–8 GB) and whether your machine has a compatible GPU.

To use a local model: install Ollama, pull a model (ollama pull <model>), then enter the model name in CARL's model field in the format model:tag — for example, llama3:8b or qwen2.5:14b.

Analyses with AI

To use AI narration on any analysis, set the Output Mode selector to Raw + LLM before clicking Run. The Raw output is generated first and then passed to the selected Output Model for rephrasing. Both outputs are shown together in the output panel.

Raw output is always the authoritative result. If the AI output conflicts with the Raw output, trust the Raw output and treat the AI version as a draft requiring correction.

Fast and Full modes

The LLM Mode selector (visible in Raw + LLM mode) controls how thoroughly the model output is processed:

  • Fast — the Output Model rephrases the Raw output once and the result is displayed immediately. No verification is performed. Suitable for exploratory work or when a quick readable draft is needed.
  • Full — the Output Model rephrases as in Fast mode, but the result is then passed to the Verification Model, which reviews the AI description against the Raw output and flags any discrepancies, omissions, or potential hallucinations — including any change to the spelling of a taxon name. The verification report is displayed below the description. Full mode makes two model calls per analysis and is slower, but provides an additional check for any output intended for formal or published use.

The two roles have different requirements. The Output Model needs fluency and the ability to follow formatting instructions; the Verification Model needs strong critical-reading and reasoning ability. Models with dedicated reasoning or "thinking" capabilities tend to perform best as the Verification Model.

Output model = writer  |  Verification model = editor.

LLM settings

Configured in Settings → LLM Settings:

  • Output Model — the model used to narrate analysis output
  • Verification Model — the model used for Full-mode checking
  • Carl Model — the model that powers the chatbot
  • Temperature — controls output variability (0 = highly deterministic; higher values = more varied prose). For formal taxonomic output, a low temperature (0.1–0.3) is generally recommended.

Response length is sized automatically from each model's real context window and the actual content being sent for that call — there is no Max Tokens setting. This is worked out per model and per call, so the Output Model, the Verification Model, and the correction pass that runs when Full-mode verification finds issues are each sized from their own real limits, not a single shared number.

Style guides

A style guide is a plain-text or Markdown file that is injected directly into the prompt for every analysis. It is the primary mechanism for controlling writing style — users can specify preferred terminology, sentence structure, level of detail, or formatting conventions, and the model will attempt to follow them.

CARL ships with two built-in style guides:

  • minimal_style_guide.md — a short set of basic conventions. The default; works well for most datasets.
  • intermediate_style_guide.md — more detailed instructions for structure and terminology; suitable for users who want more formally styled or consistent output.

Write your own style guide as a plain text file and select it via the Browse button in Settings. A separate style guide can optionally be specified for the Verification Model — if none is set, it inherits the Output Model's guide. Keep style guides concise: a long or complex guide may compete with the main task instruction in smaller models.

Iterating on style. Generate a description of a single well-known taxon, read the output, adjust the style guide, and repeat. Iterate until satisfied before running the full dataset.

Hallucinations and Best Practice

All language models can hallucinate — produce fluent, confident text that is factually incorrect. A model may invent a species name, misquote a measurement, or describe a character state not present in the data. This is an inherent property of how language models work, not a software bug, and no model is immune.

In a taxonomic context, hallucination is particularly consequential. An incorrect character state, a fabricated citation, or a wrong species name in a formal description can cause lasting confusion in the literature.

How CARL reduces hallucination risk:

  • Models work from Raw Output, not from memory. Because the model is asked to rephrase a deterministic, matrix-derived input rather than generate content from scratch, the scope for hallucination is substantially reduced. The model cannot easily insert information that is not already in the Raw Output.
  • Raw Output is always shown. Every AI description appears alongside its Raw Output, making it straightforward to spot any discrepancy.
  • Full mode adds a verification step. The Verification Model reads both the Raw Output and the AI description and flags inconsistencies. This does not guarantee correctness, but provides an additional layer of checking.

Best practice:

  • Always compare AI output against Raw Output before using it.
  • Use Full mode for any output intended for publication or formal use.
  • Treat AI output as a first draft requiring editorial review, not a finished product.
  • Be especially cautious with species names, measurements, and any information the model could plausibly have encountered in its training data — these are the most likely candidates for hallucination.
  • Larger, API-hosted models hallucinate less than small local models, but no model is immune.
AI output should never be incorporated into formal taxonomic work without independent verification against the original data and the primary literature.
